MVP vs. Full Scope: What We Promised vs. What We're Building

Scope awareness: We added significant scope when we combined two course milestone projects (AI and Big Data) into one integrated system. The sections below describe the full academic scope. But the original commitment to our client is simpler, and that commitment comes first.

MVP: What We Promised the Client (Minimum Viable Product)

We committed to delivering a tool similar to a Google Gemini Gem or a Claude Project -- a configured LLM workspace where HR can:

  1. Paste a stale position description into the tool
  2. Receive a classification recommendation (up to 2 career group/role matches)
  3. Receive a compensation range recommendation (W&M salary grade, e.g., S15)
  4. Read the LLM's reasoning for why it chose that classification

This is achievable with what we have today: our DHRM reference data (56 career groups, 294 roles, pay crosswalk) loaded as context into any LLM, plus the classification prompt template (v1). No ML model, no multi-agent system, no H2O required. If everything else falls through, the client still gets what they were promised.

Current Pipeline (What Exists Today)

The current system is a prompt-based pipeline: scrape DHRM reference data, structure it into tables, and provide it as context to an LLM along with a position description. The LLM does all the classification reasoning.

Figure 1: Current Architecture (Prompt-Based)

The gap: The current pipeline has no confidence signal. The LLM says "this is a Financial Services Manager III" but there's no quantitative measure of how certain that classification is. HR has to trust the LLM's self-reported reasoning -- which is persuasive but not verifiable. The red "???" in the output is what we're proposing to fix.

Proposed Architecture: Hybrid ML + LLM

We're proposing a three-stage "trust but verify" architecture inspired by how banks process loan applications: a quantitative pre-screen (credit score), an expert reviewer (underwriter), and a compliance audit (QC). Each stage uses a different technique, so when they agree, confidence is high.

Figure 2: Proposed Architecture (Hybrid ML + LLM)

The Banking Analogy

Think of how a bank processes a loan application:

BankingGRIFFINPurpose
Credit score (FICO) ML model shortlist Fast, quantitative, consistent pre-screen
Underwriter review LLM classification Nuanced judgment on full context
Compliance audit Confidence + fairness check Ensures no bias, flags uncertainty
No credit history != reject Missing SOC codes != lower classification Absence of data is not negative signal
Protected class compliance (ECOA) Occupational family fairness check No systematic under-classification of historically undervalued roles

Why Three Stages Instead of One?

  • Redundancy builds trust: When ML and LLM independently agree, HR can act with confidence. When they disagree, that's a signal to apply human judgment -- not a failure.
  • Different failure modes: ML models fail on out-of-distribution inputs (novel roles). LLMs fail on hallucination and inconsistency. By combining them, we cover each other's blind spots.
  • Auditability: Every classification comes with: (a) what the ML model predicted and why (SHAP), (b) what the LLM decided and why (narrative), (c) whether they agreed (confidence), and (d) whether fairness flags were triggered. This is an audit trail HR can defend.

Data Strategy for ML Training

DONE (Mar 31): Workday scrape complete. 150 total postings fetched from W&M's public Workday JSON API (williammary.wd12.myworkdayjobs.com/WM). 103 staff PDs retained, 47 faculty excluded per client direction. Labels extracted: comp_grade (100%), job_profile_code (95%), job_family (97%). All raw JSON cached in raw_workday/. CQM quality control passed (4 checkpoints, 36 criteria). Zero label leakage confirmed.
The design challenge: These postings are published job ads that already contain the classification answer (pay grade, job profile, job family). But when HR actually uses our tool, they'll be classifying a new PD that has no classification yet. So we must strip all classification/pay fields from the training input and teach the model to predict from duties, qualifications, and context alone. Training on uncensored PDs would just teach the model to read the label -- which is useless.

Recommended Approach: Feature Engineering + Weighted Sources

Instead of training on raw PD text (which needs thousands of examples), we extract structured features from each position description and train on those. This turns a text classification problem into a tabular classification problem -- and H2O's GBM/RF handles 149 tabular rows well.

Proposed features (extracted from each PD by LLM or regex):

Cross-Course Synergy (Both Professors Should Notice)

  • Interpretability at every layer: SHAP for ML, natural language for LLM, confidence scoring for the combined output. This isn't a black box -- it's a glass box.
  • The "credit score" framing: Missing data (sparse SOC codes, no historical titles) doesn't penalize a classification -- just like a thin credit file shouldn't auto-reject a loan applicant. We handle missing features explicitly.
  • Compliance / fairness: Historically undervalued occupational families (clerical, custodial) shouldn't be systematically under-classified compared to traditionally valued ones (IT, financial). The fairness guard checks for this.
