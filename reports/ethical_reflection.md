## Introduction

GRIFFIN is an AI-powered tool that classifies Virginia state position descriptions into DHRM career groups and pay bands. Because the system directly influences how positions are categorized and compensated, ethical considerations are not an afterthought but a design constraint woven into every stage of the pipeline. This reflection documents the specific practices we implemented to ensure GRIFFIN operates responsibly, transparently, and with appropriate human oversight.

## Public Data Ethics

All source data for the DHRM career group taxonomy was scraped from the Virginia Department of Human Resource Management website, which publishes career group definitions, pay band structures, and classification criteria as public government records. No private, proprietary, or access-restricted data was used.

Even though the data is publicly available, we implemented responsible scraping practices. Our pipeline notebook (`notebooks/2_dhrm_pipeline.ipynb`) includes a 1.5-second delay between HTTP requests (`time.sleep(1.5)`) and caches every downloaded page locally so each URL is fetched at most once. The notebook explicitly documents this rationale: "All DHRM career group pages are public government data. We add a polite delay between requests and cache locally so each page is downloaded at most once." This approach minimizes server load on a government resource while ensuring reproducibility.

Position descriptions used for ML training were collected from William & Mary's public Workday career site (williammary.wd12.myworkdayjobs.com). All postings are publicly accessible without authentication — no login, API key, or click-through agreement is required to view them. William & Mary is a public university and its job postings are government employment records. Collection used rate-limited requests (1.5-second delays) with local caching so each posting was fetched at most once. The Workday platform's robots.txt does not disallow the API path used for data collection.

## Classification Bias and Fairness

Our training dataset consists of 103 William & Mary position descriptions, which presents inherent limitations. The class distribution is heavily skewed: Administrative Services accounts for 55 of the 103 records, while Engineering and Technology has only 4, and Health and Human Services has just 3. This imbalance means the model has far more evidence for some occupational families than others, and predictions for underrepresented categories carry higher uncertainty.

We address this limitation in two ways. First, the feature engineering notebook (`notebooks/4_feature_engineering.ipynb`) explicitly documents the class distribution and flags it as a modeling consideration for the H2O AutoML stage, where stratified cross-validation preserves class proportions across folds. Second, and more fundamentally, GRIFFIN is designed as an advisory tool. The system outputs a classification recommendation with an explicit confidence score (1-100), an alternative match, and detailed reasoning. It never makes a final determination. The small dataset and class imbalance reinforce why human judgment must remain the decision-making authority.

## Human-in-the-Loop Design

GRIFFIN's Streamlit application (`app/streamlit_app.py`) embodies a human-in-the-loop architecture. The workflow is deliberately structured: an HR professional pastes a position description, the AI produces a recommended career group, role, and pay band, and then the professional evaluates the recommendation before taking action. The interface displays a confidence percentage, classification reasoning, and an alternative career group match, giving the user the information needed to accept, modify, or override the AI's suggestion.

The tool never auto-submits classifications, never writes to any HR system, and never removes the human from the decision loop. This design reflects a core principle: AI should augment HR expertise, not replace it. Classification decisions affect employee compensation and career progression, and that authority must remain with qualified professionals.

## LLM Transparency and Explainability

A common criticism of AI systems is that they function as opaque "black boxes." GRIFFIN addresses this at multiple levels. In the Streamlit app, every classification includes a structured reasoning narrative generated by the LLM that references specific duties from the position description and maps them to DHRM classification criteria (Complexity, Results, Accountability). Users can toggle a detailed AI explanation that provides 3-4 sentences of domain-specific rationale.

The LangChain multi-agent system (`app/griffin_langchain_agents.py`) extends this transparency further. The classifier agent's system prompt instructs it to "always explain your reasoning step-by-step," and the orchestrator coordinates a visible workflow: first classify into a career group, then match to a specific role, then determine compensation. Each step produces traceable output rather than a single unexplained answer. The agent architecture with 8 distinct components (LLM initialization, agent creation, message handling, streaming, custom tools, external API tools, memory, and multi-agent orchestration) makes the reasoning pipeline auditable from end to end.

## Data Privacy and Handling

Position descriptions from William & Mary's Workday system undergo a rigorous censoring pipeline before any ML training occurs. Notebook 3 (`notebooks/3_workday_scrape.ipynb`) implements a two-phase process: HTML-to-plain-text conversion followed by line-by-line censoring against 30+ skip patterns. The censoring removes all classification-revealing metadata including job profile codes (JP numbers), compensation grades (S/H codes), job requisition IDs, dollar amounts and salary ranges, job family labels, FLSA status lines, and EEO boilerplate. The notebook documents the rationale: these fields would constitute data leakage, producing models that "look perfect in training but fail completely in production."

The training dataset (`workday_training.csv`) deliberately excludes raw text, containing only censored text and labels. The feature engineering notebook operates entirely on the `censored_text` column, and even notes that `budget_amount_max` was dropped as a feature because dollar amounts were already stripped during censoring. No personally identifiable information (names, contact information, or individual salary data) appears in the training pipeline.

## API Key Security and Responsible Deployment

GRIFFIN uses multiple external APIs (Google Gemini, Tavily, CareerOneStop), each requiring authentication credentials. These keys are managed through environment variables loaded from a `.env` file that is explicitly excluded from version control via `.gitignore` (which lists `.env` and `*.env`). The repository includes a `.env.example` file with placeholder values (`your-google-api-key-here`, `your-tavily-api-key-here`, etc.) so collaborators can configure their own credentials without exposing any real keys.

Both the Streamlit app and the LangChain agent system load credentials using `python-dotenv` and read from `os.environ`, with explicit checks and user-facing error messages when keys are missing. At no point are API keys hardcoded in source files. The LangChain module comments reinforce this: "API keys loaded from environment -- never hardcoded in source."

## Conclusion

GRIFFIN's ethical posture is not a separate compliance exercise but an integrated set of engineering decisions: rate-limited scraping of public data, transparent censoring of training inputs, confidence-scored recommendations with visible reasoning, human-in-the-loop architecture that preserves professional authority, and credential management that prevents secret exposure. Each of these practices is implemented in code, documented in notebooks, and verifiable by any reviewer examining the repository. As AI tools increasingly enter HR workflows, this grounded, auditable approach to responsible development is essential.
